## AI 開發規則

### 修改前說明

- 說明問題與解決方案時附上具體例子，交代輸入、原行為及預期結果，讓使用者能直接理解影響；不只列抽象規則或專業名詞。
- 修改程式碼前先核對相關現況，按改動規模簡述實作及驗證方式；重要設計說清業務結果、現有能力、最簡方案及必要新增的取捨，局部修改只說相關差異，不機械列出完整 Class／流程清單。需要使用者決定的業務語意或重大取捨先詢問，已明確且已授權的部分直接執行。

### 產品目標與開發原則

- **核心產品定位**：本專案是個人**全市場**美股分析、估值及選股系統，以實用覆蓋率、資料正確性、查詢／排程效能及程式碼可維護性為優先。核心用途是協助使用者判斷個股當前估值在**自身歷史區間與同業比較中處於高位還是低位**、結合產業倍數假設換算**價格參考區間與假設價格區間**（明確標示為市場比較基準或產業假設情境，不等同內在價值或買賣指令），並搭配均線（如年線 `SMA200`）、支撐阻力及動能指標輔助觀察進出場條件。
- **全市場通用覆蓋與例外停追開關**：
  - 資料同步與估值計算預設涵蓋**全市場所有有效美股**（包含科技、消費零售、醫療、工業、能源、礦業原物料、公用事業、通訊、REITs／MLP、銀行與保險，以及採用 `US_GAAP` 或 `IFRS` 同幣別報表的跨國企業），絕不寫死僅支援少數板塊。財報與股價幣別不同時維持不自動匯兌（`REPORTING_CURRENCY_MISMATCH`）。
  - 股票主檔的人工追蹤開關（`stock.tracked`，預設 `true`，JPA 標註 `@ColumnDefault("true")`）用於排除使用者明確停追的個別標的；主檔同步任務不得覆寫既有股票的 `tracked` 設定。停追股票不再作為獨立財報同步、估值輸出與選股目標，但若與其他 `tracked = true` 股票共用同一發行人 `cik`（或作為大盤基準 ETF），仍須同步計算所需的關聯行情與拆股資料，避免多股類關聯計算斷鏈。
- **主流覆蓋優先，禁止過度防禦與「零誤差配平」封殺**：不做假設性的防禦設計，亦不為極少數標的之供應商欄位歸類差異堆疊特例補丁。「不補零、不猜自訂標籤」是指**缺少核心財務分母或股份經濟範圍不一致時不捏造假數字**，**絕非**要求財報子科目必須零誤差相加等於合計項才放行主表已披露的權威總額：
  - 普通股權益與 EV 債務／租賃：未披露優先股或優先股為 0 時，直接採用母公司股東權益總額（`StockholdersEquity`），不強制要求五項權益子科目零誤差配平；有優先股（如銀行、公用事業、REITs）時，P/B 扣除優先股帳面值，EV 以優先股及少數股東權益帳面值作標準近似（EV 缺少數股東權益、缺優先股標籤或無短期借款明細時視為 0）。EV 租賃按會計準則分流：`US_GAAP` 優先排除已披露的營運租賃負債，若缺租賃拆分明細但已有不含租賃之純借款（`CURRENT_DEBT` + `LONG_TERM_DEBT`）則直接採純借款計算 EV；`IFRS`（同 TTM 期間準則一致時）因採單一承租人模型，EV 債務直接包含全部租賃負債以維持分子分母口徑一致。
  - 營業收入與自由現金流：非金融營運企業缺少 `Revenues`／`SalesRevenueNet` 時，直接採用標準合約收入（`RevenueFromContractWithCustomerExcludingAssessedTax`），不強制要求損益表同時列示 `GrossProfit` 與營業成本配平。FCF 優先採用富途已提供的 `FREE_CASH_FLOW`；合成 FCF 時須使用完整資本支出（如 SEC `PaymentsToAcquireProductiveAssets` 或 `PaymentsToAcquirePropertyPlantAndEquipment`），避免誤將單一軟件資本化明細當成總資本支出。
  - 營運口徑 EBITDA：全市場非金融營運企業統一採用 `Operating Profit + DD&A`（支援 `US_GAAP` 與 `IFRS`，同一 TTM 四期準則須一致）；損益表缺折舊攤銷時，直接接受富途或 SEC 現金流量表標準折舊攤銷總額標籤（包含能源與礦業的折耗 `Depletion`、公用事業與重工業的棄置負債攤提 `Accretion`、科技與媒體的無形／內容攤銷），並在計算口徑說明中標註，不為剔除單一細項而接入數 GB 的 EDGAR 原始申報 HTML 解析或維護英文列名白名單。
  - 流通股數基準與多股類工程準則：統一以扣除庫藏股後的**流通在外股數（`outstandingShares`）**為基準，移除僅依股票名稱含 `Class A/B/C` 即封殺市值及強制要求 `split_from_date` 覆蓋的過度攔截（無拆股錯誤時直接依 `stock_split` 計算因子）。計算同發行人多股類時排除 `ADR` 干擾；多股類公司不得將兩類等值市值重複相加，歷史市值倍數僅在確認來源提供等值股數，或最新扣除庫藏股後的等值總股數與同日拆股調整後之 SEC 申報流通股數吻合（誤差 `<= 2%`，符合 1:1 經濟權結構）時採用申報股數計算，否則標記 `SHARE_CLASS_ECONOMIC_BASIS_UNVERIFIED`。
  - 產業模型與估值參考邊界：統一以 `stock.sic` 與 `industry_valuation_config` 集中判定銀行、保險與證券經紀業，核心指標為 `P/E`、`P/B`，`P/FCF` 與 `EV/EBITDA` 標記為 `NOT_APPLICABLE`。`historicalReference` 須先選定單一適用主指標貫穿整段 5 年序列計算分位數（不得逐月切換指標，金融業亦不得退回不適用指標）；`peerReference` 按發行人 `coalesce(cik, figi)` 去重計為一家公司；查詢指定歷史日期時，`peerReference` 與 `industryAssumption` 統一標記為 `NOT_APPLICABLE`（此防穿越僅限市場同業快照與參考設定日期，歷史估值本身的財報分母仍沿用同財季最新修訂規則）。
- **財季配對與「存財季分母、即時算歷史倍數」架構**：
  - 行情底座保留自 2016 年起的未復權日線（`stock_quote`）與拆股紀錄（`stock_split`）。
  - 估值資料層持久化**標準化財季分母**（`stock_financial_period`，以 `(figi, period_end)` 為主鍵，正規化為 SEC 實際結算日、無 SEC 時採富途結算日，`fiscal_year`／`fiscal_quarter` 為可空標籤；保存 `period_start`、14 項核心財務原料、TTM 分母與期末流通股數基準）及**最新交易日估值快照**（`stock_valuation_latest`，供全市場選股篩選與排序）；不再維護千萬列日頻估值結果表，亦不維護跨批次舊值拼湊（`reconcile`）狀態機。
  - SEC 財務事實同步讀取整份 CIK JSON 時，按與資料庫 `NULLS NOT DISTINCT` 唯一約束一致的披露鍵直接比對數值與財季標記，有新增或內容變更即更新入庫；當某股票有新財報、修訂或拆股變更時，直接**整股重建該股票全部財季分母**並刷新最新估值快照（免除的是全市場歷史每日估值表的重算）。
  - 歷史估值（含個股分析 5 年月末序列與指定歷史交易日查詢）優先配對 `period_start <= D <= period_end` 的財季分母列，若該期尚未入庫則回退 `period_end < D` 的最近一列，在查詢時與未復權收盤價**即時相除**，不改為 Point-in-Time 回測口徑。
  - 同一報期以 `period_end` 相差 `<= 7` 天且同期間類型（單季或年度）配對 Futu 與 SEC，以 Futu 為主、SEC 標準標籤補缺，不得跨報期補值。跨越拆股日的歷史單季 EPS，僅在採拆股後提交之直接申報 EPS，或經 SEC `WeightedAverageNumberOfDilutedSharesOutstanding` 與對應盈利驗證股份基準一致時放行。
- **外部來源從簡與過時文件清理**：為外部資料缺口新增自建流程前，先查核現有 API 與官方輕量批量檔（如 Massive、Alpaca、Futu、SEC `companyfacts.zip` 與 `submissions.zip`）的能力，優先採用低維護成本方案。當 `README.md` 等既有文件的舊實作細節與本文件原則或使用者本次確認的設計衝突時，以本文件與最新確認設計為準，並於修改程式時同步更新 `README.md`，不得因舊文件文字保留已淘汰的複雜流程。

### DEV 變更提交與追溯

- 已確認 DEV 的本次相關修改通過相稱驗證後，自動 commit 並 push 目前 DEV 分支。僅可自動提交正式維護的 `.java`、`.ts`、`.tsx`、`.properties`、`.md`；其他檔案類型須使用者當次明確授權。提交不代表部署。
- 提交前核對 staged／unstaged 差異，只納入本次相關檔案；不得混入生成物、臨時檔、憑證或他人修改，也不得為提交清理或還原無關變更。
- Commit 標題統一使用 `<type>: <繁體中文摘要>` 格式，依實際變更選擇 `fix`（修正）、`feat`（功能）、`refactor`（重構）、`docs`（文件）、`test`（測試）、`perf`（效能）或 `chore`（維護）等分類前綴；不得省略前綴，程式名稱可保留原文。說明使用繁體中文，記錄修改原因、實際變更、驗證與未驗證限制；後續追查原因時使用 git log／blame。禁止無根據的完成宣稱、force push 或覆寫遠端；push 失敗如實回報。
- 純文件修改核對內容及差異即可，不為此啟動 backend 或重跑 Job。

### 測試與臨時產物

- 依變更影響選擇 targeted tests 及必要的代表性 DEV API／Job 驗收；啟動前確認環境、連線目標、埠佔用與既有工作，不重複執行無關排程。
- 驗收估值同步與計算時，限定全市場跨類型代表性股票（涵蓋一般營運企業、銀行／保險、單一與雙上市多股類、拆股公司、能源礦業、公用事業、`IFRS` 同幣別跨國股及租賃／外幣邊界樣本），核對入庫的財季分母、最新估值快照、歷史即時估值及富途觀察倍數。
- AI 自行啟動的 backend 或測試程序，在驗收後結束並核對釋放資源；不得停止使用者原有程序，除非使用者明確要求。
- 正式自動化測試及必要 fixture 應可獨立重現，保存在 `src/test`；不依賴未納入專案的本機檔案。一次性日誌、驗證工具與臨時產物放專案外暫存並於完成後清理。
- 不為單次修改另外建立重構或驗收報告 Markdown；結果在對話中交付，長期使用說明更新既有正式文件。

### 程式碼修改後的 Scenario 交付

- 每次修改程式碼後，在對話用表格列出本次相關的 Scenario Test Cases，逐項對照「情境／條件、修改前的實際行為、修改後的預期行為、實際測試狀態」，讓使用者直觀看到改變與原因。正常、邊界、失敗與重跑情況按本次改動選取，不必機械列滿。
- 清楚區分已執行測試與尚未驗證的預期情境，不為列出 Scenario 額外產生測試報告或不必要的自動化測試。

### 程式碼可讀性與簡潔性

- 優先採用清楚、直接、易維護的寫法；不為減少行數使用難讀的巢狀條件、Stream 或 lambda，也不為假設需求新增多餘抽象、wrapper、Interface 或 Helper。
- Method／Class 按實際職責拆分，避免過長方法與無意義轉呼叫；同一業務計算優先重用既有入口，不建立平行實作。
- Service 依現有業務領域整理 package，相關測試採對應 package；不為分類額外新增轉發用 Service、Interface 或 Helper。
- 僅供單一 Schedule 使用、沒有其他呼叫端的流程留在該 Schedule，以 private method 拆分細節；不為分層形式另建專用 Service。已有共用或來源專屬能力則繼續重用。
- 通用業務程式與查詢按實際用途命名；直接依賴第三方 API 或處理其來源專屬資料時才在名稱標示來源。
- Schedule 的 `execute()`／`executeInternal()` 應依序呈現日期範圍、目標選取、取數、提交及失敗處理。參數解析、篩選細節和批次處理交給命名清楚的方法，入口保留流程順序。Controller 所呼叫的 Service 第一個入口 Method 應清楚呈現 API 主要流程。重要處理階段加入簡短註釋。
- 只為測試或驗收而限定資料範圍的參數與邏輯留在測試程式，正式排程只接收有實際使用需求的參數。
- 簡潔不得犧牲業務正確性、交易一致性、必要錯誤處理及效能。

### Java 排版

- Java 區域變數禁止使用 `var`，包含測試，必須寫明型別。
- 保持緊湊易讀；合理長度的 throw、log、method call、簡單條件及 return 維持單行，僅在過長或明顯改善可讀性時拆行。
- Java setter 一行一個 statement，不合併多個 setter，也不為單一 setter 無必要拆行。

### Entity 欄位註解

- Entity 的持久化業務欄位以簡潔中文 `@Comment` 說明實際意義；特別註明容易混淆的來源、財務期間、公開／觀察時間、單位、股數及 NULL 語意。已有正確註解沿用，不增加「保存某欄位」等空泛文字。
- 複合主鍵的影子 ID Class 集中放在 `model.entity.key`，其欄位及不對應獨立資料庫欄位的投影關聯不重複註解。`ddl-auto=none` 時，新增 `@Comment` 只變更 Entity 映射；既有資料庫的欄位註解另由受控 schema 變更同步。

### SQL 查詢與程式簡化

- 業務表、欄位及約束以 JPA Entity 維護。除非使用者當次明確要求，勿在專案目錄新增獨立的 `.sql` 檔案，包括建表、遷移、資料種子、查核及一次性修復腳本。既有 Quartz 建表腳本 `src/main/resources/db/quartz/postgresql.sql` 保留，由 `QuartzSchemaBootstrap` 管理。
- 新股的 `stock_status` 由 `StockDailyTask` 在新增股票的同一交易建立；下游排程只更新已存在的狀態列。
- 資料庫結構以清楚的實體關係、正式欄位及主鍵／外鍵／唯一約束維護完整性；冗餘欄位或 JSON 權威資料須有實際需求及明確一致性規則。
- 優先以可走索引的 WHERE／JOIN 一次查取本輪需要的資料，避免 N+1、迴圈查詢和無謂的全表讀取。涉及並行或多階段更新時，依實際交易契約於寫入前重查必要狀態。
- 修改 SQL／JPQL 時核對結果基數、NULL、重複列、排序／分頁與交易語意；不為減少查詢數量而堆疊難維護的深層 JOIN、複雜 OR 或額外架構。

### 程式碼效能與效率

- 主動檢查與本次修改相關的重複 SQL、資料量、檔案／網路 I/O、外部 API 次數、記憶體及批次交易成本；差異不明時先估算或小範圍量測。
- 串行、並行與批次方式依實際工作量、來源限流、執行緒安全及交易邊界選擇，不因形式上的「最佳實務」增加複雜性。
- 沒有真實瓶頸或明確需求時，不額外建立快取、多層重試／恢復、持久化 checkpoint 或抽象框架，也不為效能優化改變業務結果。

### 資料正確性與外部來源

- SEC 文件只解析標準 taxonomy 標籤（例如 `us-gaap`、`dei`）；企業自訂標籤的定義因公司而異，本專案不解析或以其補值。標準標籤缺少所需資料時，保留缺值及原因，不猜測自訂標籤的含義。
- 正常計算以正式流程已入庫的業務資料與既有資料契約為依據，保留必要的輸入及一致性檢查；沒有具體異常、來源修正或已確認的重驗需求時，不預設重新抓取來源、重驗全部輸入或建立獨立證據層。
- 新增 hash、版本或完整性驗證前，說明實際用途與成本，區分下載損壞、內容變更／去重與防止惡意竄改。不得為未確認的威脅自行建立證據鏈；檔案與基準 hash 均可被修改時，不宣稱單靠比對即可防竄改。
- 資料缺失或估值輸入異常時，沿正式來源、解析、入庫及計算流程核查，區分來源缺失、同步未完成與程式錯誤；不以推測值、補零、其他股票或未公開資料製造有效結果，但負值分母（負 EPS／負 FCF／負 EBITDA／負普通股權益）須明確標為 `NOT_APPLICABLE`（N.M.）並保留實際財務數值供畫面展示。

### 時間規則

- 業務程式取得現在時間使用共用的 `DateTimeService`。
- 交易日、開收市時間及歷史收市截點直接共用 `MarketStatusService`，不另加轉呼叫的日曆服務。
- 對使用者顯示的系統與排程時間採香港時間；交易日、財報公開時間及外部來源日期保留各自的市場語意，不擅自換算或推測。
